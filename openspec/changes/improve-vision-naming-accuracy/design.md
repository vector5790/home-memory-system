## Context

当前线上链路已经切到本地 YOLOX 主体检测、native CLIP region embedding、native 二进制索引检索，性能基本可接受。命名准确性成为主要问题：同一客厅图中电视、功放、唱片机、音箱等外观相近或语义相近物品容易被检索到“投影仪”等错误类目。现有链路以 embedding TopK + 类目聚合 + 阈值接受为主，缺少系统化错误归因、细粒度类目/品牌/形态补充、候选可纠正率评估和用户反馈闭环。

命名不准可能来自多个层面：

- 主体框问题：框包含背景、多个物体、只框到局部，导致 crop embedding 偏移。
- 索引覆盖问题：目标类目没有足够相似的真实索引图，或家庭长尾物品缺失。
- 类目粒度问题：GPC-style 四级类目不足以区分功放、唱片机、投影仪、电视盒、音箱等家庭影音设备。
- embedding 模型问题：CLIP 对细粒度商品/型号/功能差异区分能力有限，正确和错误 Top1 score 可能重叠。
- 阈值策略问题：全局阈值无法覆盖类目簇差异，高相似错误会被误接受。
- 候选展示问题：Top1 错但 Top3 有正确候选时，系统应让用户低成本纠正，而不是直接定名。

## Goals / Non-Goals

**Goals:**

- 建立命名准确性诊断数据结构，记录每个主体从检测到最终命名的关键证据。
- 产出离线评测报告，区分主体召回、命名 Top1、Top3、候选可纠正率、误接受率、未命名率和混淆簇。
- 为错误样本生成可执行归因结论：补索引、补别名、拆细类目、调阈值、候选展示或主体框修正。
- 支持用户在 App 内校正命名，并把校正信息沉淀成本地反馈样本。
- 为高混淆类目引入 cluster-level 阈值和候选策略，而不是依赖单一全局阈值。

**Non-Goals:**

- 本 change 不更换主体检测模型，不新增主体检测模型 fallback。
- 本 change 不以继续优化耗时为核心目标。
- 本 change 不要求立即引入云端识别或远程 LLM 命名。
- 本 change 不要求一次性补齐所有家庭物品索引，但必须给出补索引优先级。

## Decisions

1. **把命名评测拆成“框是否可命名”和“名称是否正确”两层**

   主体检测框错误会污染命名评估。如果一个 crop 本身不是目标物体，命名错误不能完全归因于 embedding 或索引。因此评测报告必须先判断主框是否可用于命名，再评估 Top1/Top3 命名。

2. **保留 Top3 候选作为用户可纠正路径**

   当前 embedding score 单独不足以判定高置信，正确和错误样本分数有重叠。Top1 错但 Top3 有正确候选时，系统应展示候选并记录用户选择，以提高实际导入体验。

3. **用类目 cluster 做阈值和混淆分析**

   家庭影音、小家电、容器收纳、厨房器具等簇的相似外观和语义差异不同。全局阈值会导致高混淆簇误接受，低混淆簇过度拒绝。系统需要按 cluster 统计 score/margin，并支持 cluster-level 接受策略。

4. **建立索引覆盖诊断，而不是盲目扩大索引**

   每个错误样本需要判断 TopK 是否出现同类索引、同类索引最高排名、代表图是否相似、是否缺失品牌/形态/型号。只有被归因为覆盖不足或粒度不足时，才进入补索引或拆类目任务。

5. **用户反馈优先本地沉淀**

   用户选择候选、手动改名、标记无匹配、调整主体框，都应作为本地反馈记录。反馈先用于本地报告和补索引建议，不要求立即上传或训练。

## Risks / Trade-offs

- **误把框错误当作命名错误** → 评测报告必须显示主体框截图，并记录框可命名性。
- **Top3 候选增加 UI 复杂度** → 默认仍突出推荐名，但提供候选和“都不对/手动输入”入口。
- **cluster 阈值过拟合小样本** → 报告必须显示每个 cluster 的样本数，样本不足时只给建议不自动调策略。
- **metadata-only index 与 native binary index 不一致** → 构建脚本必须从同一个 JSON 源生成二者，并记录 sourceIndex/version。
- **用户反馈数据质量不稳定** → 反馈记录必须带原图、框、候选、用户动作和时间戳，后续可过滤低质量样本。

## Migration Plan

1. 保持当前命名链路不变，先增加诊断字段和离线报告。
2. 在 App 候选面板展示 Top3 和手动纠错入口，记录本地反馈。
3. 基于报告识别高优先级混淆簇，补索引或拆细类目。
4. 对每个 cluster 试算阈值和候选策略，只在评测通过后应用。
5. 保留旧 JSON index fallback；native binary / metadata index 继续由构建脚本生成。

## Open Questions

- 家庭影音等高混淆簇是否需要引入五级“功能/设备类型”或品牌/型号层级？
- 用户手动输入的名称是否应自动创建本地自定义类目，还是只作为别名反馈？
- 是否需要引入轻量图文 reranker 或商品领域 embedding 模型来处理细粒度商品差异？
