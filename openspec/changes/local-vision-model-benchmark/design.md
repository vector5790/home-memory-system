## Context

The app already has browser-local code paths for Grounding DINO, OWL-ViT, SlimSAM, and CLIP through Transformers.js, but the runtime currently depends on whether `vendor/vision-manifest.json` and model files exist. Without assets, the capture flow can degrade to non-model Canvas region proposals; earlier code also allowed remote model loading, which makes privacy, latency, and benchmark results ambiguous.

The project now has a real-photo evaluation dataset and generated reports, but the current real report is GT-assisted. It validates the reporting harness and Top3 display, not real local model performance. The next step must run actual local models against the same dataset and compare detector/namer configurations by both accuracy and latency.

## Goals / Non-Goals

**Goals:**

- Make local vision model execution explicit, diagnosable, and reproducible.
- Require local `vendor/` assets for real model runs and clearly separate model results from Canvas fallback baselines.
- Benchmark multiple local configurations: Grounding DINO, OWL-ViT, Grounding DINO + SlimSAM, OWL-ViT + SlimSAM, CLIP embedding naming, and Canvas fallback baseline.
- Extend `vision-model-eval-report` to include per-stage timing and per-provider summary metrics.
- Keep all validation script-driven; do not require browser inspection.

**Non-Goals:**

- Do not introduce a paid or cloud model as part of default recognition.
- Do not build the full industrial image index in this change.
- Do not claim accuracy for GT-assisted predictions as real model performance.
- Do not replace user correction, placeholder naming, or inventory confirmation flows.

## Decisions

1. Disable remote model loading by default.

   The runtime should set `allowRemoteModels=false` unless an explicit development flag enables remote model loading. This keeps user photos local and makes benchmark results independent of network conditions.

   Alternative considered: keep remote HuggingFace/CDN model loading as a fallback. That helps demos on a fresh checkout, but it makes privacy and timing semantics unclear. For this project, a clear local-asset preflight is better than a hidden network fallback.

2. Add a model asset preflight before benchmark execution.

   The benchmark runner should verify that `vendor/vision-manifest.json` exists, runtime assets are present, and each requested model has the required files. It should report missing assets with actionable download instructions instead of silently skipping real models.

   Alternative considered: let each model fail lazily during the benchmark. That produces partial reports but wastes time and hides setup issues inside per-image failures.

3. Use a simulator/CLI benchmark boundary instead of browser inspection.

   The report should be generated by a script command that consumes a dataset, model matrix, local assets, and index. The script should produce predictions, raw timing traces, JSON report, Markdown report, and HTML report.

   Alternative considered: drive the app UI and scrape state. That is closer to end-user behavior, but it is slower and less deterministic. The UI can still consume the same local model adapter later.

4. Separate provider configurations in the output schema.

   Each prediction batch should include `providerId`, model IDs, enabled stages, asset versions, and timing fields. The report should group metrics by provider, not just by image, so Grounding DINO vs OWL-ViT vs fallback comparisons are obvious.

   Alternative considered: run one provider at a time and compare separate reports manually. That is simple to implement but makes regressions harder to spot.

5. Measure staged timing as first-class data.

   Timing should include at least model load/warmup, detection, segmentation, crop preparation, embedding, retrieval, naming, and end-to-end time. Summary metrics should include p50/p95 and failure counts.

   Alternative considered: only record end-to-end time. That is easier, but it does not reveal whether bottlenecks are model load, detection, SAM, or CLIP.

6. Keep GT-assisted and Canvas baselines in reports but mark them as baselines.

   GT-assisted output is useful for report harness validation. Canvas fallback is useful as a non-model lower baseline. Both must be structurally labeled so they cannot be mistaken for real local model accuracy.

   Alternative considered: remove baselines once real models are added. Keeping them helps distinguish report failure from model failure.

7. Use conservative acceptance criteria before product use.

   A first pass should require each real local provider report to include enough images to compute metrics and should surface go/no-go status. Suggested initial gates: box recall at IoU 0.5, name accuracy, combined accuracy, top-3 retrieval accuracy, p95 latency, and failure rate.

   Alternative considered: accept any working local model. That would move faster, but the product cost of wrong item names is high.

## Risks / Trade-offs

- Local model assets are large and may fail to download -> Keep `download-vision-assets.py` idempotent and add asset preflight with exact missing paths.
- Browser Transformers.js and CLI adapters may not share every API -> Put shared provider semantics and output schema in the benchmark contract, then adapt implementation per environment.
- Local model inference may be slow on some machines -> Report p50/p95 and per-stage timing, and keep Canvas fallback as a user-visible degradation path.
- Small real-photo dataset can overstate accuracy -> Treat the first report as smoke/evaluation, not a production benchmark; expand dataset before full indexing.
- CLIP embedding index currently has proxy vectors in generated fixtures -> Report must distinguish proxy/GT-assisted index runs from measured CLIP embedding runs.
- Detector errors can cascade into naming errors -> Report both detection-only metrics and end-to-end naming metrics.

## Migration Plan

1. Add local model preflight command and make remote model use opt-in only.
2. Implement a benchmark model matrix and prediction output schema with stage timings.
3. Run real local providers against the real-photo dataset and generated index.
4. Generate combined JSON/Markdown/HTML reports with provider comparison tables.
5. Update README with setup, benchmark, and interpretation instructions.
6. Keep rollback simple: disable benchmark integration and keep the existing Canvas fallback/manual correction path.

## Open Questions

- Should the first benchmark execute local models through Transformers.js in a headless browser runtime, a Node adapter, or a Python/ONNX adapter?
- What minimum dataset size should be required before using benchmark gates to approve full index generation?
- Should latency gates be calibrated per machine class, or only reported without pass/fail at first?
- Should CLIP naming be evaluated against the real-photo index only, or also against a larger open-license gallery once available?
